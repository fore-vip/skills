# 参考案例：美容台账 H5（云服务接通版）

> 这是**第二个**用本模板生成的实例，用来证明「换一份 spec 就换一个业务」，并补上第一个实例没走到的云服务分支。AUTO 站点在这里只是参考，不是依赖。

## 一、任务与事实源

用户只给了一句「cloud service 按 SKILL 走一遍，主题是 美容」。按 P0 顺序查过：全库、工作区、资产库均无「美容」既有定义，因此**事实源就是这条指令本身**，不再挤牙膏式追问。

P1 判据命中第 1 条（待办状态要跨刷新保留），所以需要后端；用户又明确点名云服务，按规范直接 `inspect` → `activate`，确认由平台确认框收集。

## 二、六阶段实际走了什么

| 阶段 | 动作 | 结果 |
|---|---|---|
| P0 | 检索 + 确认事实源 | 无既有定义，方向明确，不再问 |
| P1 | `inspect`（count=0）→ `activate`（create） | 确认框通过，`billingStatus=normal` / `provisionStatus=assigned` |
| P2 | 新建 `app.spec.json`（美容主题）+ 云模式生成 | 只改数据，模板与生成器共用；柱图提示随 spec 换成护理口径 |
| P3 | 独立应用，**跳过站点接线** | 没有首页卡、分享卡、sitemap，这些是既有站点才做的适配层 |
| P4 | 生成自检 / 静态引用 / 真实视口断言 / 截图目视 / 云端写入读回 | 11 项断言全 PASS，三张 390 视口截图目视正常 |
| P5 | 本地预览、回写模板、归档 | **未上线**；发布需复用同一个 applicationId |

## 三、云端落点

- 应用：`美容台账`，web 形态，`domainPrefix=beauty-salon`。
- 表 `beauty_tasks`：`id`、`task_id`（唯一）、`state`、`note`、`updated_at`。没有登录，属于**应用级共享演示台账**，页面「说明与边界」里写明任何人都能改状态、不要放真实顾客资料。
- RLS：开启，授权 `authenticated, anon`，读 / 插 / 改三条策略，不给删除策略（应用不删数据）。
- 前端：CDN SDK 初始化一次 client，只做 `select` 与 `upsert`；`endpoint` / `oauthRelayBaseUrl` / `publishableKey` 全部来自 `publicConfig`。页面自带云端状态条，连通与各类失败都有可见提示。

## 四、验证证据（关键数字）

- 管理侧：插入 4 行 → 读回 4 行 → 冲突更新 `b1` → 再读回 `b1=ok`。
- 前端：一次连通运行中点击「确认」，`b1` 从 `pending` 变 `ok`（数据库读回为证）；重新加载后剩余数由 4 件变 3 件，首条待办呈已确认样式，状态条显示已连通。
- 失败路径：屏蔽 SDK 后显示「云端组件没加载出来」，待办仍 4 件、本地交互照常；CDN 抖动的几次运行也没有把本地操作说成已存云端。
- 视口：CDP 强制 390×844，11 项断言全 PASS，`scrollWidth=390` 无横向溢出；首屏 / 演示区 / 使用方式三图目视无截断、无重叠、无错位。

## 五、这一实例逼出来的模板改动

1. 生成器新增 `--cloud-config` / `--cloud-table` 云模式，纯前端仍严格零外链、云模式只允许 SDK 白名单。
2. 演示脚本暴露 `window.H5AppApply` / `H5AppOnAction` 两个钩子，云适配层读写状态而不侵入演示逻辑。
3. `demo.lowLabel` 让柱图提示可配，不再把「品类动销偏快」硬编码到所有行业。
4. `verify_viewport.mjs` 增加 `--wait`，云页面可留足 SDK 加载时间。
5. 主文档补「确认框通过」分支，参考文档补 CDN 抖动、回读滞后、断言复位等坑。

## 六、边界

- 页面**未上线**，只在本地预览端口可访问；激活不等于发布。
- 经营数字、店名、顾客、回话全是示例数据；页面首屏、演示区、说明区三处都写明了口径。
- 未开放安装，没有接真实门店系统，没有登录，没有把顾客资料入库。
- 发布时要用同一个 applicationId，否则域名变化会让 Origin 精确匹配失败。
