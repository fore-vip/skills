# 内容口径与红线

## 一句话

**页面是给主题的读者看的，不是给做页面的人看的。** 任何一句读起来需要知道「这是怎么生成的」才能懂，就该删掉。

## 叙事顺序（线性，不许倒置）

```
首屏价值主张 → 具体项目 / 能力 → 可信证据（案例 / 数字 / 引语） → 行动（预约 / 留资） → 常见疑问
```

`sections` 数组顺序就是页面顺序，`verify_static.py` 会逐项比对。硬性检查：`hero` 在最前、`cta` 存在且不是第一个区块。

不许出现：
- 先铺一堆数字，最后一屏才说「这是什么」
- 先教「怎么用」，最后才交代「现在到哪一步」
- 正文最后突然跳到另一个项目的「出品 / 作者主页 / 联系方式」

## 文案框架（专家按主题现场写）

| 位置 | 要回答的问题 | 写法 |
|---|---|---|
| `hero.h1 + em` | 关我什么事 | 主题专属的一句话，不用通用营销腔 |
| `hero.p` | 凭什么信 | 具体做法、具体边界，不写「赋能 / 一站式 / 颠覆」 |
| `features` | 到底有什么 | 每项写清对象、时长 / 条件、价格或代价 |
| `showcase` | 实际怎么发生 | 过程摊开讲，减少第一次来的不确定 |
| `quote` / `stats` | 别人怎么说 | 数字要标口径，引语要标来源，不编造权威背书 |
| `cta` | 现在做什么 | 说明留什么信息、会不会有人联系、数据去哪 |
| `faq` | 还担心什么 | 回答最具体的顾虑，不写套话 |

## 主题词审计

每个 spec 必填：

- `meta.requiredTerms`：主题必备词，缺一个 FAIL。美容例：`护理 / 皮肤 / 预约 / 美容`
- `meta.forbiddenTerms`：本主题不该出现的词。至少覆盖**其他主题的典型词**（美容页禁 `营业额 / 订单数 / 客单价`；科技产品页禁 `美容 / 护理 / SPA`）、**其他项目品牌**、**旧模板口径**

`verify_static.py` 还会叠加一份通用制作过程词表（`生成器 / spec.json / SKILL / 模板生成 / 激活云服务 / publicConfig / applicationId / H5App / 前凌智选 / AUTO 工作室 / 示例数据原型 / KPI / 待办清单 / 现场演示`），出现在可见正文里一律 FAIL。检查前会剔除 `<head> / <script> / <style>`，技术字符串不算正文。

## 这次真实踩过的坑（别重犯）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 只把门店 spec 的标签换成美容词 | 美容页出现「护理成交额 / 到店人次 / 单次均价」，KPI 公式仍是营收÷人次 | 版式与内容结构一起换，按主题重写 spec |
| 品牌沿用别的项目的名字 | 页眉「前凌智选」、结尾「AUTO 工作室 · 微信 … · 作者主页」，读者完全看不懂 | 品牌由本主题定，页眉 / 页脚 / 正文一致 |
| 把制作过程写进正文 | 「这是一台按模板生成的移动应用：云服务已激活」 | 过程写进交付说明和 references，不写进页面 |
| 开头说「状态存云端刷新不丢」，结尾又说「预览连不上 / 未开放」 | 前后矛盾 | 一句话口径写进 `disclaimer`，全文只按这一句说 |
| 「现在到哪一步」放最后一屏 | 顺序颠倒 | 价值主张放首屏，边界放 CTA 的 note 与页脚 |
| 换主题后柱状图提示还是「N 个品类动销偏快」 | 骨架没换干净 | 不预设任何业务板块，section 全由 spec 决定 |

## 口径一致性

`meta.disclaimer` 必须原样出现在正文（通常放 `cta.note`），生成器与静态闸门都会检查。全文关于「是不是示例 / 有没有上线 / 数据存不存」只允许这一种说法。表单不接后端就明说「没有发送、也不会保存」；接了演示表就明说「只写入演示表，不会有人联系你」。**绝不假装成功**。

## 业务事实必须有来源（v3 新增）

页面里凡涉及真实经营的信息——**店名、地址、电话、营业时间、项目名、时长、价格、经营承诺、顾客评价**——一律不得由 AI 臆造。必须逐条登记在 `meta.facts`：

```json
{ "key": "示例价目", "value": "¥198 等", "source": "example" }
```

`source` 只能是 `user`（用户提供）、`placeholder`（占位待填）、`example`（示例）。含 `example` 时 `meta.factReview` 必须为 `true`、口径声明必须含「示例 / 演示」，交付说明附「待补事实清单」；这类页面是**演示应用，禁止作为真实门店对外发布**。

用户没给真实信息时，一次性列出待补清单并停在 INCOMPLETE，禁止用编造值补齐后当作完成。静态闸门会核对 `facts` 完整性、来源合法性与示例标注，交付判定会核对闭环。

## CTA 承诺必须等于实际能力（v3 新增）

- `cloud.needed=true` → 才允许「预约 / 提交 / 立即」这类强行动词，且表单可提交。
- `cloud.needed=false` → 表单整体禁用，CTA 文案降级为「看看项目 / 了解流程」；页面明确写「页面草稿，表单未开放」。
- **禁止把「没有发送 / 不会保存 / 未开放」写成 PASS 断言的 expect**：那等于把业务不可用变成验收项。
- `meta.disclaimer` 必须与 `cta.note` **逐字一致**并原样出现在正文，生成器会检查；全文只允许这一种口径，不许前后矛盾。
