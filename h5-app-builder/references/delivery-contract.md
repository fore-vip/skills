# 交付形态契约与应用创建

> 这是 v3 最重要的设定。它回答「什么算做完」，防止再次交出「只设计了一个首页」。

## 一、为什么加这一层

2026-11-12 用户单独调用专家后的复盘：专家按当时的 SKILL 跑完了 P0–P4，产出 `index.html`（20749 字节）、spec、四张 390px 截图，`verify_static.py` 16/16、`verify_viewport.mjs` 29/29 全部 PASS，然后停下汇报。交付目录里**没有 `.genie`、没有 `applications.yaml`、没有部署产物**，专家自己的记忆写着「未 git 提交、未上线、未发布 SkillHub」「本地 127.0.0.1:8791 预览」。

页面上有导航「预约护理」、Hero「约一次到店护理」、表单「提交预约意向（示例）」，但 `meta.cloud.needed=false`，提交逻辑只弹「没有发送，也不会保存」；`canonical / og:url / ld+json.url` 三处都是 `https://example.com/index.html`。用户的原话是「**并没有发起应用的创建（只是设计了一个首页）**」。

根因不是专家偷懒：**当时 P5 的终点就是「本地预览 + 说明未上线」**，流程里没有创建应用这一步；四道闸门全部只检查页面内部质量，没有任何一道能判定「这到底是不是一个应用」。所以全绿与「半成品」可以同时成立。

## 二、三态定义

`verify_delivery.py` 是唯一能宣布完成的闸门，输出三态：

| 状态 | 含义 | 允许怎么汇报 |
|---|---|---|
| `DELIVERED` | 应用实体、业务动作、站点地址、事实来源全部闭环 | 可以写「已交付」；未取得在线链接仍需写「未上线」；含示例事实要写「演示应用，禁止作为真实门店对外发布」 |
| `DRAFT` | 用户明确同意的页面草稿 | 标题必须写「页面草稿，不是应用」，附转应用步骤，**禁止写「应用已完成」** |
| `INCOMPLETE` | 诉求与产物不匹配，或关键闭环缺失 | **禁止汇报完成**，逐条列缺项与补齐命令 |

判定顺序：先查页面与形态合法性 → 再比对 `meta.intent` 与 `meta.deliverable` → 再按形态查应用实体 / 站点 / 后端 / 事实 → 最后查「有没有把业务不可用写成验收项」与截图覆盖度。任一硬项失败即 INCOMPLETE。

## 三、形态判定表

| 用户话里的信号 | 形态 | 必做 |
|---|---|---|
| 应用 / 上线 / 发布 / 可访问链接 / 能收预约 / 留资 / 落库 / 后端 | `webapp` | P3.5 全套 + 真实站点地址 + 云端表单 |
| 部署到站点 / 官网页面 | `site` | 站点地址 + 部署记录 + 五道闸门 |
| 先看看效果 / 做个草稿 / 只要设计 / 对比版式 | `draft` | 不写假域名、表单禁用、附转应用步骤 |

**默认不是 draft**。用户只说「做个 XX 宣传页」而没有明确说草稿时，按 `webapp` 处理；若因信息不足无法创建应用，判 INCOMPLETE 并一次性索要缺失事实，不要擅自降级成草稿后当作完成。

`meta.intent` 必须原样记录用户当轮指令，`verify_delivery.py` 用它比对诉求；`meta.deliverable` 是专家的判定结果，两者一起留证。

## 四、P3.5 应用创建六步

1. **inspect**：`workbuddy_cloud_service action=inspect` 看本会话已有应用；有合适的复用，没有才 `action=activate`（`applicationMode=create`，`appName` 用主题名，`domainPrefix` 用主题拼音或英文，`appType=web`）。
2. **确认框**：由平台弹出，不由专家代替用户决定。`cancelled: true` → 记录 cancelled，停在 INCOMPLETE，**不重试、不绕路、不静默降级成 localStorage 后谎称已接后端**。
3. **配置边界**：只把 `endpoint / oauthRelayBaseUrl / publishableKey` 写进前端；`applicationId / resourceId` 等管理侧标识不进页面。
4. **建表**：业务表 + `ENABLE ROW LEVEL SECURITY` + GRANT + 读/写策略；管理侧跑「插入 → 读回 → 冲突更新 → 再读回」并把结果写进交付说明。
5. **重新生成**：`meta.deliverable=webapp`、`meta.siteUrl=真实域名`、`meta.cloud.needed=true` 且填 `table/columns`；用 `--cloud-config` 与 `--base-url` 重新生成，前端只做 `select / insert`。
6. **发布路径**：发布为应用 / 站点上线需要用户明确指令，但交付说明必须给出可执行命令清单。发布要复用同一个 applicationId，否则域名变化会让 Origin 精确匹配失败。

没有登录时，数据表是**应用级共享演示数据**：页面「说明与边界」要写明任何人都能改状态、别放真实顾客资料，不伪装成私有数据。

## 五、失败与降级口径

| 情况 | 处置 |
|---|---|
| 云服务确认框被取消 | `INCOMPLETE`；如实写 cancelled，给下次激活命令；不重试 |
| CDN 在本机时通时不通 | 页面给可见提示「云端组件没加载出来，本次提交不会保存」；不得把本地操作说成已存云端 |
| 缺真实业务事实 | 一次性列「待补事实清单」，`facts` 里标 `placeholder`；禁止用编造值补齐后对外发布 |
| 浏览器里没跑通写入读回 | 不写「已接通」，只写「管理侧已验证 / 前端未验证」及原因 |
| 用户没下令发布 | 写「未上线」，并给出发布命令；不把「代码已提交」「预演通过」混同为上线 |

## 六、交付说明模板

```
产出文件：<index.html / spec / .genie / shots 数量>
版式与理由：<id> 命中 <关键词>，与另一主题的差异是 <...>
交付形态：<webapp|site|draft> | 判定：<DELIVERED|DRAFT|INCOMPLETE>
五道闸门：① 自检 PASS ② 静态 N 项 ③ 双视口 N 项 ④ 逐段截图 N 张 ⑤ 交付判定 <状态>
六角色自检：产品 / UI / 开发 / 测试 / 店长 / 用户 逐条结论
云服务：接了什么 / 没接 / 取消原因 / 写入读回证据
未做事项：未上线 / 未发布 SkillHub / 待补事实清单
下一步命令：<激活、生成、发布各一条可执行命令>
```

## 七、与其他闸门的关系

静态闸门与视口闸门只回答「页面好不好」，交付判定回答「东西对不对」。因此**不能用 ② ③ 全绿替代 ⑤**；反过来，⑤ 也要求截图覆盖全部区块，证明 ③ ④ 确实跑过。三道脚本返回非零退出码表示失败，不要只看最后一行输出就宣布通过。
